## 2. Open: PR #9 — free run allowance (`feat/tester-run-allowance`)

https://github.com/dmuranov/testpilot/pull/9

### Why

Prospects should be able to run **three** tests on the free tier — same app or
different ones, scenario / flow / security — for the next day or two, then the
free tier goes back to one run. Longer term, allowlisted demo emails keep a
small allowance for recording walkthroughs.

### What it does

The account **stays on plan `free`** — that is what the dashboard, the free
security scan and the `ANTHROPIC_SUPPORT_KEY` funding all key off. An *extra*
run is one started while `free_run_used` (or the free security scan) is already
used. The mechanism lives in `lib/free-runs.js`; `server.js` decides how many
runs an identity gets and which endpoints take one.

| Step | Where | Rule |
|------|-------|------|
| gate | `/api/test`, multirole, flow, `chat/start`, security `api-intercept` | `reserveExtraRun()` takes the extra **synchronously**, so two parallel requests cannot both take the last one |
| early 4xx / error | any response sent without a commit | the hold is released the moment the handler sends a response (wraps `res.end`), even to a client that already left |
| client abort mid-handler | — | **not** a release: the handler may still start the run, and it stays charged |
| commit | right before each endpoint's success response | the spend is recorded and persisted |
| refund | the endpoints' existing "no verdict → refund" blocks | give back **what was spent**: an extra via `hold.refund()` (once per committed hold), the base run via the existing `free_run_used` reset. Same "only a verdict counts" rule as the base run and the paid credit |
| reported | `/api/auth/me`, `/api/funnel/start` | `free_run_used` reads `false` while *unspent* extras remain (`remaining()`, which ignores in-flight holds, so another tab merely holding the last extra does not paint a paywall); the dashboard keeps sending `freeRun: true` |
| app slots | `/api/funnel/start`, `/api/learn` | `appSlotsFor()` = `max(plan.apps, 1 + runs left)`, so runs may be on different apps but an exhausted identity cannot open new support-key crawls; both 402s report the limit actually applied. `/api/learn`'s cookie-less path passes no identity (no widening); the funnel passes its body email because it is the path that mints the session |
| persistence | `./free-runs-used.json` (gitignored, tmp+rename, serialised) | only committed spends; in-flight holds are memory, so a restart mid-request charges nothing; load is additive and awaits its own save; **fail-closed** (no extras) until the file has been read; a corrupt file is moved aside as `.corrupt`, never overwritten |
| safety | `holdTtlMs` (15 min) | a handler that never answers releases its hold instead of pinning it for the life of the process |

Keyed by `canonicalEmail`, so gmail dots / plus-aliases are one identity.

**Who may spend an extra.** `/api/test` and `/api/learn` honour extras (and
widened app slots) only with a cookie session — their cookie-less paths take
the email from the body. multirole / flow / chat / security go through
`requireUser`, which also accepts header auth, so a header-authenticated
integration can spend extras there but not on `/api/test`. The funnel mints a
cookie session for any syntactically valid email, so this rule only stops
drive-by API use; the real bound on support-key spend is the existing daily
budget ceiling, exactly as for the base run today.

### Knobs

| Env | Default | Meaning |
|-----|---------|---------|
| `TESTPILOT_FREE_RUNS` | **3 — temporary** (commit `b9886b8`, which changes only the `FREE_RUNS_DEFAULT` line); code default is otherwise 1 | runs per free identity; `0`/`1` = no extras. It is a *code* default rather than an env on the box because the only deploy path from here is push-to-main; the env still wins when set. While it is 3, `TESTER_EMAILS` makes no difference |
| `TESTPILOT_TESTER_RUNS` | 3 | runs for emails in `TESTPILOT_TESTER_EMAILS` (kept after the revert) |
| `TESTPILOT_TESTER_EMAILS` | empty | comma-separated allowlist |

### What it does not change

- The base free run and the base free security scan remain the two separate
  pools they are today; only the extras are shared. With `FREE_RUNS=3` an
  identity can do 3 runs **plus** the one free scan it already gets.
- The base run's own check-then-act window (two requests both reading
  `free_run_used=false` before either burns it) predates this PR.
- Dashboard copy still says "one free test run" — cosmetic, left for the two days.
- `free_run_used` on `/api/auth/me` is the derived "no runs left" value, not the raw flag.
